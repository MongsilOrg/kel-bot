# KelBot — 기능 명세서

이터널 리턴 KEL 스크림 자동 신청·추첨 Discord 봇.
scrimbot의 Python 스택(discord.py + 파일 기반 영속화)을 그대로 사용하나, MMR/조편성/시드/이미지 생성 등은 제거하고 **지역 기반 팀 신청 + 우선권 시스템 + 8팀 랜덤 추첨**에 집중한다.

---

## 1. 개요

| 항목 | 내용 |
|------|------|
| 봇 이름 | kelbot |
| 핵심 기능 | 지역 단위 팀 신청, 매일 자동 랜덤 추첨, 우선권 자동 관리 |
| 추첨 정원 | **8팀** |
| 추첨 방식 | 우선권 자동 확정 → 잔여 슬롯 랜덤 추첨 |
| 운영 휴일 | 없음 (대회일 포함 매일 운영) |
| 시간대 | KST (`Asia/Seoul`) |

레이팅/MMR 없음. 시드팀 없음. 조편성/방코드/공지 자동화는 1차 범위에서 제외 (필요 시 2차 확장).

## 2. 일일 운영 타임라인

```
                  D-1                                      D                                D+1
   ─────────┬──────────┬────────┬────────────────┬──────────────┬──────────────┬───────────
            │          │        │                │              │              │
         (이전일       21:00    00:30           17:00          21:00           ...
         스크림        리셋    1차 추첨       최종 데드라인   다음일 리셋
         종료)      신청 오픈    (≥8팀)        (8팀 미달 시
                                              스크림 취소)
```

| 시각 (KST) | 이벤트 | 설명 |
|------------|--------|------|
| **21:00 (D-1)** | 신청 리셋 / 오픈 | 전일 신청자/결과 정리. 우선권 보유자 명단 확정. D의 신청 접수 시작. |
| **00:30 (D)** | 1차 랜덤 추첨 | 신청 ≥8팀이면 추첨 실행. <8팀이면 보류. |
| **00:30 ~ 17:00 (D)** | 보류 추첨 대기 | 8팀 도달 즉시 자동 추첨. |
| **17:00 (D)** | 최종 데드라인 | 8팀 미달 시 당일 KEL 스크림 취소. D를 위한 우선권은 모두 소멸(이월 없음, §4 참조). |
| **21:00 (D)** | 다음 일자 리셋 | 우선권 갱신/소멸, 신청 데이터 초기화. |

### 운영 규칙

- 신청 창구는 **21:00 ~ 17:00 (익일)** 사이만 열림.
- 그 외 시간에는 대시보드 `신청`·`취소` 버튼이 ephemeral 안내 메시지로 응답 (`현재 신청 받지 않는 시간대입니다.`).
- **신청 마감 시점 = (즉시 추첨 완료 시점) 또는 (17:00) 중 먼저 오는 것**.
- 추첨 완료 후에는 **그날 추가 신청·취소 모두 불가** (§5 참조).
- 추첨 전에는 본인 신청 취소 가능. 취소된 신청은 추첨 대상에서 제외.
- **17:00 데드라인은 우선권보다 항상 우선**. 17:00 시점에 미사용 우선권은 즉시 소멸. 추첨 미실행 시에도 17:00에 모든 활동 종료.

## 3. 신청 데이터 모델

### 팀 신청

| 필드 | 타입 | 설명 |
|------|------|------|
| `team_id` | `str (uuid4)` | 내부 식별자 |
| `region` | `str` | 지역명 (예: `부산`, `경기`, `대전`). 신청자 닉네임에서 파싱 |
| `applicant_id` | `str` | 신청자 Discord user ID (snowflake) |
| `applicant_display` | `str` | 신청자 Discord 닉네임 — **반드시 `지역) 닉네임` 형식** (§3.1 검증) |
| `applied_at` | `str (ISO8601)` | 신청 시각 |
| `scrim_date` | `str (YYYY-MM-DD)` | 어느 일자의 스크림에 신청한 것인지 (= 21:00 리셋 기준 D) |
| `had_priority` | `bool` | 이 신청에 우선권이 적용되었는지 (추첨 시 확정) |
| `status` | `enum` | `pending`(추첨 전) / `selected`(8팀 확정) / `rejected`(탈락) / `cancelled`(취소) |

### 3.1 닉네임 형식 검증

- 신청 시 신청자 Discord 닉네임이 `<지역>) <닉네임>` 형식인지 검사.
- 정규식 예: `^(?P<region>[^)\s]+)\)\s*\S+`
- **형식 미준수 시 신청 거절** — 에러 메시지로 형식 안내.
- 파싱된 `region`은 양쪽 공백만 제거하고 그대로 사용. 별도 정규화/매핑 없음(서버에서 닉네임 규칙으로 통일됨 가정).
- **닉네임 캡처 시점 = 신청 시점**. 신청 후 Discord 닉네임이 변경되어도 신청 레코드의 `applicant_display`/`region`은 신청 시점 값으로 고정.

### 3.2 중복 신청 방지

해당 스크림 일자(`scrim_date`) 단위로 적용:

- **1 user = 1 신청**: 같은 `applicant_id`로 두 번째 신청 시도 시 거절.
- **1 region = 1 신청**: 같은 `region`이 이미 등록된 상태에서 다른 user가 같은 지역으로 신청 시 거절.
- 자발 취소 후 재신청 가능 — 단, 닉네임이 동일하므로 자동으로 같은 지역으로만 재신청됨 (다른 지역 신청은 닉네임 변경 후 가능하나 위 규칙으로 또 차단됨).

### 우선권 (Priority)

| 필드 | 타입 | 설명 |
|------|------|------|
| `region` | `str` | 우선권 보유 지역 (지역이 식별 키) |
| `granted_at` | `str (ISO8601)` | 발급 시각 (탈락한 직후) |
| `valid_for_date` | `str (YYYY-MM-DD)` | 이 우선권이 적용되는 스크림 일자 (= 발급 다음 날) |
| `consumed` | `bool` | 사용 여부 (해당 일자 신청 후 추첨에서 확정되면 true) |

**키 = 지역명.** 닉네임이 아닌 지역으로 추적 → 같은 지역이 신청자만 바뀌어도 우선권 유지 가능 (§10 항목 1, 확정).

## 4. 우선권 (Priority) 규칙

### 발급
- **추첨이 실제로 실행된 경우에만 발급**.
- 추첨 시 신청 팀이 8을 초과 → 탈락(rejected) 팀(지역)에 **D+1 우선권 발급**.
- 1차 추첨(00:30)이든 8팀 즉시 추첨이든 동일.
- **8팀 미달로 추첨이 미실행된 날(스크림 취소된 날)에는 우선권 발급 없음.**
- 자발 취소(추첨 전)된 신청은 우선권 발급 대상 아님.

### 우선권 키 = 지역
- 우선권은 **지역명** 기준으로 발급/추적. 같은 지역이면 신청자(user_id)가 달라져도 동일 우선권 사용.

### 적용
- 다음 날(D+1) 신청 시 자동 매칭 (지역 일치).
- 추첨 시 우선권 보유 지역은 **랜덤 추첨에 앞서 8팀 슬롯에 자동 확정**.
- 우선권 자동 확정 후 남는 슬롯만 일반 신청 팀 중 랜덤 추첨.
- **8팀 정원은 (우선권 자동 확정 팀 + 일반 신청 팀) 합산 기준**. 합계 8 미달이면 추첨 미실행(보류).

### 예시
- D에 11팀 신청 → 8팀 랜덤 추첨, 3팀 탈락 → 탈락 3팀(지역 기준)에 D+1 우선권.
- D+1에 9팀 신청 (우선권 보유 3팀 모두 포함) → 우선권 3팀 자동 확정 + 잔여 5팀은 일반 6팀 중 랜덤 → 1팀 탈락 → D+2 우선권.

### 소멸
- **추첨 실행 시점** 또는 **17:00 데드라인** 중 **먼저 오는 시점**에 미사용 우선권 즉시 소멸. 데드라인이 우선권보다 항상 우선.
- 다음 날(D+1) **행사(추첨)가 어떤 사유로든 미실행**되면 보유 우선권은 무조건 소멸. 이월 없음.
- 우선권은 **하루만 유효** — D+1에 사용/소멸되며 D+2로 이월 없음.
- 자발 취소 후 D+1 17:00 전 + 추첨 전 재신청 시 같은 일자에 한해 우선권 재사용 가능.

### 우선권 정원 = 추첨 정원
- **우선권 총 수는 8을 넘지 못함** (= 추첨 정원과 동일 캡).
- 이전 추첨에서 탈락한 팀이 9팀 이상인 이론적 경우, **신청 시각이 빠른 순으로 상위 8팀에만 우선권 발급**, 나머지는 발급 없음.

## 5. UI — 대시보드 단일 진입

**슬래시 명령어·관리자 명령어 일절 사용하지 않음.** 사용자의 모든 액션은 영구 대시보드의 LayoutView 버튼으로만 처리. 봇은 완전 자동 운영되며, 운영 사고 대응은 §7.3 응급 대응(JSON 수정 + 봇 재시작)에 따른다.

### 5.1 신청 대시보드

- 지정된 채널(`APPLY_CHANNEL_ID`)에 봇 시작 시 영구 메시지 1개 게시.
- 메시지 ID는 `data/dashboard_message.json`에 저장 → 봇 재시작 후 동일 메시지에 컴포넌트 재바인딩.
- 메시지가 삭제되었거나 ID 매칭 실패 시 봇이 **자동으로 재생성** (별도 명령어 불필요).
- 대시보드 LayoutView 구성:
  - **현재 신청 상태 표시 영역** — 신청 팀 수 / 정원 8, 오늘의 우선권 보유 지역 목록, 추첨 상태(대기/보류/완료/취소), 신청 창 오픈/마감 여부.
  - **신청 팀 목록** — 지역명 기준 나열, 우선권 적용 팀은 별도 표시 (예: `★ 부산`).
  - **버튼 2개**:
    - `신청` — 닉네임 형식 검증 + 중복 검증 후 신청 등록. 실패 시 ephemeral 에러 메시지로 사유 안내.
    - `취소` — 본인 신청만 취소 (추첨 전에 한함). 확인 LayoutView(`CancelConfirmView` 패턴) 제시 후 확정.
- **모달 없음** — 신청 시 사용자 입력 받지 않고 Discord 닉네임에서 자동 파싱.
- **버튼 쿨다운** — scrimbot 패턴(`_button_cooldowns`)으로 동일 user의 연속 클릭 차단 (1~2초).
- 신청/취소/추첨/리셋 이벤트마다 대시보드 LayoutView 자동 갱신 (메시지 edit).
- 일일 21:00 리셋 시 대시보드 표시도 새 일자 상태로 갱신.
- 신청 창 마감(추첨 완료 또는 17:00) 후에는 `신청`·`취소` 버튼 클릭 시 ephemeral 안내(`현재 신청 받지 않는 시간대입니다.`).

### 5.2 추첨 결과 공지

- 추첨 실행 시 별도 채널(`NOTICE_CHANNEL_ID`)에 LayoutView 메시지 게시.
- 포함 항목:
  - 선정된 8팀(지역) 목록
  - 탈락 팀(지역) — **"내일 우선권 부여" 안내 문구 함께 표시**
  - 추첨 시각, 다음 일자 신청 오픈 시각(21:00)
- **일반 Embed 사용 금지** — 모든 출력은 LayoutView 컴포넌트로.

## 6. 자동화 스케줄러

| 작업 | cron (KST) | 동작 |
|------|-----------|------|
| 일일 리셋 | `0 23 * * *` | 신청 데이터 초기화, 새 일자(D+1) 신청 창 오픈, 대시보드 갱신 |
| 1차 추첨 | `30 0 * * *` | ≥8팀(우선권+일반 합산) → 추첨 실행, <8팀 → 보류 모드 진입 |
| 데드라인 처리 | `0 17 * * *` | <8팀 상태면 당일 스크림 취소 공지 + 미사용 우선권 모두 소멸 |
| 즉시 추첨 트리거 | 신청/취소 이벤트 | 보류 모드 중 누적 신청(우선권+일반) = 8 도달 시 즉시 추첨. 추첨 후 신청 창 종료 |

구현: scrimbot과 동일하게 `discord.ext.tasks` 사용.

## 7. 영속화 & 봇 재시작 대응

scrimbot과 동일하게 **파일 기반 JSON 영속화** 사용 (DB 도입 불필요).

```
kelbot/
└── data/
    ├── applications.json      # 오늘 일자 신청 목록 (21:00 리셋 시 초기화)
    ├── priorities.json        # 활성 우선권 목록 (지역 키)
    └── draw_state.json        # 추첨 상태(pending/done/cancelled), 추첨 시각, 보류 플래그
```

### 7.1 저장 정책
- 모든 신청/취소/추첨/리셋 이벤트 발생 즉시 동기 기록 (scrimbot `team_data_manager.py` 패턴).
- 임시 파일에 쓰고 `os.replace`로 원자적 교체 → 쓰기 도중 크래시 방지.
- 로그 archive 별도 불필요 (UX는 추첨 결과 공지로 충족).

### 7.2 봇 재시작 시 복원 절차
scrimbot과 동일 수준의 무중단성을 보장한다.

1. **부팅 시 상태 로드** — 위 3개 JSON을 메모리에 로드. 파일 없으면 빈 상태로 초기화.
2. **누락된 스케줄 보정** (`schedule_manager.py`):
   - 현재 시각(KST) 기준으로 21:00 리셋, 00:30 추첨, 17:00 데드라인 중 **놓친 이벤트** 즉시 실행.
   - 예: 봇이 00:31에 부팅 → `draw_state.json`이 `pending`이면 즉시 추첨 트리거.
   - 예: 봇이 17:01에 부팅 → 데드라인 후처리(우선권 소멸, 보류 상태 → cancelled) 즉시 실행.
3. **신청 창 상태 재계산** — 현재 시각 기준 신청 가능 여부 재판정 (`utils/time.py`).
4. **즉시 추첨 트리거 재확인** — 보류(`pending`) 상태에서 누적 신청 ≥ 8이면 즉시 추첨.
5. **Discord 영구 메시지(대시보드 LayoutView) 핸들 복원** — 메시지 ID를 `data/`에 저장하여 재시작 후 동일 메시지에 컴포넌트 재바인딩.

> 핵심 원칙: **봇 다운타임이 운영에 영향을 주지 않도록 모든 시점 이벤트는 멱등적으로 재실행 가능**해야 한다. 추첨 완료 후 재시작 시 중복 추첨 방지를 위해 `draw_state.json`의 `done` 플래그를 우선 확인.

### 7.3 응급 대응 정책

봇은 자동 운영이 원칙이며, 관리자 UI는 제공하지 않는다. 비정상 상태 발생 시 운영자는 다음 순서로 대응한다.

1. `data/*.json` 파일 직접 수정 (서버 접근 권한 보유자만).
2. `pmc restart kelbot`으로 봇 재시작 → §7.2 복원 절차가 일관성 회복.
3. 대시보드 메시지 자체가 손상되면 `data/dashboard_message.json`만 삭제 후 재시작 → 자동 재생성.

이는 의도적 단순화 선택이며, 관리자 권한 검증/오용 가능성을 원천 차단한다.

kelbot/

│   ├── dashboard.py           # 대시보드 setup/refresh/버튼 콜백 (슬래시·관리자 명령어 없음)

    └── dashboard_message.json # 영구 메시지 ID (재시작 후 LayoutView 재바인딩)

## 10. 확정 사항 (2026-05-24)

| # | 항목 | 결정 |
|---|------|------|
| 1 | 우선권 키 | **지역명 기준** (user_id 무관) |
| 2 | 닉네임 형식 | `지역) 닉네임` 형식 **강제**. 미준수 신청은 거절 |
| 3 | 추첨 후 취소 | **불가** |
| 4 | 미달일 우선권 | **발급 없음** (추첨 미실행 = 우선권 미발급) |
| 5 | 우선권 정원 | **최대 8** (=추첨 정원). 8팀 정원 = 우선권자 + 일반 신청 합산 |
| 6 | 노쇼/자발취소 패널티 | **없음** |
| 7 | 운영 휴일 | **없음** (대회일 포함 매일 운영) |
| 8 | 데드라인 vs 우선권 | **17:00 데드라인이 항상 우선**. 다음 날 추첨 미실행 시 우선권 무조건 소멸 |
| 9 | 1 user = 1 신청 | **강제** (같은 user 중복 신청 거절) |
| 10 | 1 region = 1 신청 | **강제** (같은 지역 중복 신청 거절) |
| 11 | 닉네임 캡처 | **신청 시점**으로 고정 |
| 12 | 추첨 UI | **LayoutView** 사용 (일반 Embed 금지) |
| 13 | 사용자 UI | **대시보드 메시지 + LayoutView 버튼 `신청` / `취소` 2개** (slash 미사용) |
| 14 | UX 명시 | 추첨 결과 공지에 **"탈락 시 내일 우선권 부여"** 명확히 표시 |
| 15 | 봇 재시작 | scrimbot 수준 무중단 — 영속화 + 재시작 시 놓친 스케줄 보정 |
| 16 | 관리자 UI | **없음**. 응급 대응은 JSON 직접 수정 + 봇 재시작으로 처리(§7.3) |
| 17 | 버튼 쿨다운 | scrimbot 패턴 차용 — 동일 user 연속 클릭 1~2초 차단 |

## 11. 1차 구현 범위 (MVP)

- [ ] **영구 대시보드 메시지** (`APPLY_CHANNEL_ID`) — `신청` / `취소` 버튼
- [ ] **닉네임 `지역) 닉네임` 형식 검증 + 거절** (모달 없음, Discord 닉네임 자동 파싱)
- [ ] **중복 신청 차단** (1 user = 1 신청, 1 region = 1 신청)
- [ ] 신청/우선권/추첨 상태 JSON 영속화 + 원자적 쓰기
- [ ] 우선권 발급/적용/소멸 로직 (`models/priority.py`)
- [ ] 우선권자 자동 확정 + 잔여 슬롯 랜덤 추첨 (`models/draw_orchestrator.py`)
- [ ] 21:00 리셋 / 00:30 추첨 / 17:00 데드라인 스케줄러
- [ ] 보류 모드 + 8팀 도달 즉시 추첨 트리거
- [ ] **LayoutView 기반** 추첨 결과 공지 (탈락자에 우선권 안내 표시, `NOTICE_CHANNEL_ID`)
- [ ] **대시보드 자동 갱신** (신청/취소/추첨/리셋 이벤트마다)
- [ ] **봇 재시작 시 상태 복원 + 대시보드 메시지 재바인딩 + 놓친 스케줄 자동 보정**
- [ ] 대시보드 메시지 분실 시 자동 재생성
- [ ] 버튼 쿨다운 (scrimbot `_button_cooldowns` 패턴)
- [ ] 신청 창 마감 후 버튼 클릭 시 ephemeral 안내 메시지
